\section{Introducción}

\subsection{Objetivos del Sistema}
\begin{itemize}
    \item Simular el funcionamiento concurrente de un parque de diversiones.
    \item Gestionar el acceso controlado a recursos compartidos (atracciones).
    \item Prevenir condiciones de carrera y deadlocks.
    \item Implementar políticas de fairness en el acceso a recursos.
    \item Generar logs detallados para análisis de comportamiento.
\end{itemize}

\subsection{Tecnologías Utilizadas}
\begin{itemize}
    \item \textbf{Lenguaje:} Java 11+
    \item \textbf{Mecanismos de Sincronización:} Semaphores, Locks, Conditions, CyclicBarrier, Exchanger
    \item \textbf{Estructuras de Datos Concurrentes:} BlockingQueue, AtomicInteger, AtomicLong
    \item \textbf{Visualización:} HTML/JavaScript para análisis de logs
\end{itemize}

\subsection{Patrón Arquitectónico}

El sistema implementa una \textbf{arquitectura basada en componentes} con los siguientes principios:

\begin{itemize}
    \item \textbf{Alta cohesión:} Cada componente tiene una responsabilidad única y bien definida.
    \item \textbf{Bajo acoplamiento:} Los componentes interactúan a través de interfaces claras.
    \item \textbf{Separación de responsabilidades:} La lógica del dominio está separada de los mecanismos de sincronización.
    \item \textbf{Patrón Productor-Consumidor:} Utilizado en múltiples atracciones.
    \item \textbf{Patrón Coordinador:} El Parque actúa como coordinador central.
\end{itemize}

\subsection{Sistema de Ingreso}

\subsubsection{Molinete.java}

\textbf{Responsabilidad:} Controlar ingreso de visitantes al parque con exclusión mutua.

\textbf{Mecanismos de sincronización:}
\begin{itemize}
    \item \textbf{Semaphore(1, true):} Garantiza exclusión mutua con fairness.
    \item \textbf{BigInteger contador:} Generador de tickets protegido por la sección crítica.
    \item \textbf{Bloque finally:} Asegura liberación del semáforo incluso con excepciones.
\end{itemize}

\textbf{Prevención de condiciones de carrera:}
\begin{lstlisting}[language=Java]
// Double-check del estado del parque
if (!Reloj.operativo()) return false;
try {
    semaforo.acquire();
    // Verificar nuevamente dentro de la sección crítica
    if (!Reloj.operativo()) return false;
    // ...
} finally {
    semaforo.release();
}
\end{lstlisting}

\textbf{Responsabilidad:} Coordinador central y fachada del sistema.

\textbf{Recursos gestionados:}

    // No soy el último, espero

\subsection{Modelo de Concurrencia y Sincronización}

El \texttt{AreaPremios} implementa el patrón **Productor-Consumidor** utilizando \texttt{ReentrantLock} y \texttt{Condition}s.

\begin{enumerate}
    \item \textbf{\texttt{ReentrantLock}}: Provee \textbf{exclusión mutua} con \texttt{fairness}.
    \item \textbf{\texttt{Condition hayVisitantes}}: Condición global para el \texttt{Encargado} (consumidor).
    \item \textbf{\texttt{Condition miCondition}}: Condición \textbf{única por \texttt{Visitante}} (productor), usada para el despertar preciso.
\end{enumerate}



\subsection{Lógica de programa}

\paragraph{Método \texttt{AreaPremios.buscarMejorPremio}}
Este método implementa la **Política de Priorización de Gasto**, asegurando que el visitante siempre obtenga el premio de mayor valor que pueda pagar, si hay stock.

\begin{lstlisting}[language=Java, caption=AreaPremios.buscarMejorPremio - Lógica de Priorización]
Premio buscarMejorPremio(int fichasDisponibles) {
    lock.lock();
    try {
        Premio mejorPremio = null;
        // 1. Itera sobre el catálogo
        for (Premio premio : catalogoPremios) {
            // 2. Verifica Stock y Costo
            if (premio.hayStock() && premio.getCostoFichas() <= fichasDisponibles) {
                // 3. Prioriza el MAYOR costo
                if (mejorPremio == null || 
                    premio.getCostoFichas() > mejorPremio.getCostoFichas()) {
                    mejorPremio = premio;
                }
            }
        }
        return mejorPremio;
    } finally {
        lock.unlock();
    }
}
\end{lstlisting}

\label{sec:comedor}

\subsection{Descripción General}

El comedor contiene un conjunto fijo de mesas. Cada visitante que desea almorzar solicita una mesa libre; si no hay mesas disponibles, el visitante espera. Una vez que una mesa alcanza su capacidad máxima, todos los visitantes de la mesa comienzan a comer. Cuando todos terminan, la mesa vuelve a quedar disponible y el comedor despierta a los visitantes que estaban esperando lugar.

El sistema garantiza:
\begin{itemize}
    \item Exclusión mutua en el acceso a las mesas.
    \item Evitar deadlocks gracias al orden estricto de adquisición de locks.
    \item Despertar eficiente de hilos bloqueados.
\end{itemize}

\subsection{Clases Principales}

\subsubsection*{Comedor}
\begin{itemize}
    \item Mantiene la lista de mesas.
    \item Gestiona el lock global que controla el acceso a la búsqueda de mesas disponibles.
    \item Contiene la condición \texttt{hayLugar}, usada para suspender visitantes cuando no existen mesas disponibles.
    \item Orquesta todo el flujo de almuerzo.
\end{itemize}

\subsubsection*{Mesa}
\begin{itemize}
    \item Cada mesa tiene su propio lock para gestionar a sus visitantes.
    \item Usa la condición \texttt{mesaCompleta} para bloquear a los visitantes hasta que la mesa llegue a capacidad máxima.
    \item Controla el estado interno: visitantes sentados, bandera de ``comiendo'', y notificación al comedor cuando la mesa queda libre.
\end{itemize}

\subsection{Flujo de Ejecución Detallado}

\subsubsection*{1. Llegada del visitante}
\begin{enumerate}
    \item El visitante llama a \texttt{almorzar()}.
    \item El comedor intenta asignarle una mesa.
\end{enumerate}

\subsubsection*{2. Búsqueda de una mesa disponible}
\begin{itemize}
    \item El comedor toma su lock global.
    \item Itera sobre todas las mesas.
    \item Si una mesa está disponible y acepta al visitante con \texttt{intentarSentarse()}, el visitante es asignado.
    \item Si no existe ninguna mesa disponible, el visitante espera en la condición \texttt{hayLugar}.
\end{itemize}

\subsubsection*{3. Espera hasta completar la mesa}
\begin{itemize}
    \item Cada visitante llama \texttt{esperarYComer()} en su mesa asignada.
    \item Se bloquea en \texttt{mesaCompleta.await()} hasta que la mesa alcance su capacidad.
\end{itemize}

\subsubsection*{4. Inicio del almuerzo}
\begin{itemize}
    \item El primer visitante que detecta que la mesa está completa activa el estado \texttt{comiendo = true}.
    \item Se despierta a todos los visitantes de la mesa.
\end{itemize}

\subsubsection*{5. Finalización y liberación}
\begin{itemize}
    \item Cada visitante termina de comer y decrementa el contador de ocupación de la mesa.
    \item El último en abandonar la mesa la marca como libre.
    \item Se notifica al comedor mediante \texttt{notificarLugarDisponible()} para despertar visitantes en espera.
\end{itemize}

\subsection{Mecanismos de Concurrencia Utilizados}

\subsubsection*{Locks y Bloqueos}
\begin{itemize}
    \item Se emplea un \texttt{ReentrantLock} por mesa.
    \item Existe un lock global en el comedor para controlar asignaciones.
\end{itemize}

\subsubsection*{Condiciones}
\begin{itemize}
    \item \texttt{hayLugar}: usada por visitantes cuando no hay mesas disponibles.
    \item \texttt{mesaCompleta}: usada por las mesas para esperar a que la capacidad se complete.
\end{itemize}

\subsubsection*{Prevención de Deadlocks}
\begin{itemize}
    \item Nunca se toma el lock de \texttt{Comedor} desde dentro del lock de una \texttt{Mesa}.
    \item La notificación al comedor siempre se hace \textbf{fuera} del bloqueo de la mesa.
\end{itemize}

\section{Teatro }
\subsection{Descripción General}

El módulo \textbf{Teatro} modela un sistema concurrente donde múltiples visitantes intentan acceder a una sala y varios asistentes se encargan de formar grupos de ingreso. El teatro funciona por tandas: cada tanda consta de la formación de 4 grupos de 5 personas. Una vez formados los grupos, comienza el espectáculo; durante este tiempo nadie puede entrar.

Se emplean hilos tanto para los asistentes como para los visitantes, y se utiliza un mecanismo de exclusión mutua mediante \texttt{ReentrantLock} y varias condiciones para coordinar estados y puntos de sincronización.

\subsection{Clases Principales}

\begin{itemize}
    \item \textbf{Teatro}: administra la cola de visitantes, los grupos, el inicio y fin del espectáculo, y coordina toda la sincronización.
    \item \textbf{Asistente}: hilo encargado de formar grupos siempre que haya suficientes visitantes y que el espectáculo no haya iniciado.
    \item \textbf{Visitante}: hilo que intenta entrar al teatro, espera ser habilitado por un asistente y participa del flujo completo del espectáculo.
\end{itemize}



\subsection{Flujo del Sistema}

\subsubsection{Visitante}
\begin{enumerate}
    \item Intenta entrar; si hay espectáculo en curso, se rechaza.
    \item Se encola en el lobby.
    \item Espera a ser habilitado por un asistente.
    \item Una vez habilitado, se sienta y espera el inicio del espectáculo.
    \item Disfruta el espectáculo.
    \item Espera el fin y se retira.
\end{enumerate}

\subsubsection{Asistente}
\begin{enumerate}
    \item Espera que haya visitantes en cola.
    \item Forma grupos de 5 personas.
    \item Cuando se formaron 4 grupos, inicia el espectáculo.
    \item Tras 10 segundos, finaliza el espectáculo.
\end{enumerate}


\subsection{Mecanismos de Sincronización Utilizados}

\begin{itemize}
    \item \textbf{ReentrantLock}: asegura exclusión mutua en toda operación crítica del teatro.
    \item \textbf{Condition hayVisitantes}: usada por los asistentes para esperar a que haya suficientes visitantes en la cola.
    \item \textbf{Condition visitantesLiberados}: los visitantes esperan aquí hasta ser seleccionados para un grupo.
    \item \textbf{Condition inicioEspectaculo}: los visitantes esperan hasta que se dé inicio oficial.
    \item \textbf{Condition finEspectaculo}: los visitantes esperan la finalización para retirarse.
\end{itemize}

\subsection{Estados del Teatro}

\begin{itemize}
    \item \textbf{esperando\_visitantes}: no hay suficientes personas para formar grupo.
    \item \textbf{formando\_grupos}: asistentes asignando grupos hasta llegar al máximo.
    \item \textbf{espectaculo\_activo}: espectáculo en curso, nadie entra ni se forman grupos.
    \item \textbf{finalizado}: se limpian grupos y se permite una nueva tanda.
\end{itemize}

\section{Realidad Virtual}

\subsection{Descripción General}
La atracción de \textbf{Realidad Virtual (VR)} permite a los visitantes disfrutar de una experiencia inmersiva. Cada visitante necesita un equipo completo compuesto por:

\begin{itemize}
    \item 1 visor de VR
    \item 2 manoplas
    \item 1 base
\end{itemize}

El sistema gestiona la entrega de componentes mediante un \textbf{Encargado} que distribuye los elementos disponibles y un registro de visitantes que están esperando o utilizando los equipos.

\subsection{Clases Principales}
\begin{itemize}
    \item \textbf{RealidadVirtual}: clase principal que coordina la asignación y devolución de equipos, así como la interacción con la ticketera para entregar fichas.
    \item \textbf{Encargado}: hilo encargado de distribuir los componentes de los equipos a los visitantes en la cola.
    \item \textbf{EquipoVR}: representa el equipo de VR de un visitante, indicando qué componentes tiene.
    \item \textbf{Pedido}: objeto que asocia un visitante con su equipo y un \textit{Condition} para esperar a que se complete.
\end{itemize}

\subsection{Variables y Mecanismos de Sincronización}

\begin{itemize}
    \item \textbf{visoresDisponibles, manoplasDisponibles, basesDisponibles}: cantidad de componentes disponibles para asignar.
    \item \textbf{cola}: \textit{Queue} de visitantes esperando su equipo completo.
    \item \textbf{equiposEnUso}: \textit{Map} de visitantes que ya tienen su equipo asignado.
    \item \textbf{lock}: \textit{ReentrantLock} para sincronizar acceso a la cola y a los recursos.
    \item \textbf{visitanteEsperando}: \textit{Condition} para que los visitantes esperen hasta que haya componentes disponibles.
    \item \textbf{mutexTicketera}: \textit{Semaphore} que asegura que un visitante acceda a la ticketera a la vez.
\end{itemize}

\subsection{Flujo de Interacción}

El flujo básico de interacción es:

\begin{enumerate}
    \item El visitante llega a la atracción y se crea un \texttt{Pedido} con su \texttt{EquipoVR}.
    \item Se agrega el pedido a la \texttt{cola} y se notifica al \texttt{Encargado}.
    \item El \texttt{Encargado} distribuye los componentes disponibles a los visitantes en orden de llegada:
    \begin{itemize}
        \item Primero se entrega el visor si está disponible.
        \item Luego se entregan las manoplas, hasta completar 2.
        \item Finalmente se entrega la base si está disponible.
    \end{itemize}
    \item Cuando el equipo está completo, el visitante es notificado mediante \texttt{Condition.signal()} y puede iniciar la experiencia VR.
    \item Tras finalizar, el visitante devuelve el equipo, actualizando los contadores de componentes disponibles y notificando a la cola en espera.
    \item Posteriormente, obtiene las fichas de la ticketera mediante un \texttt{Exchanger} protegido por un \texttt{Semaphore}.
\end{enumerate}

\subsection{Observaciones}
\begin{itemize}
    \item Se utiliza un \texttt{Lock} justo para evitar condiciones de carrera al manipular la cola y los contadores de componentes.
    \item Cada visitante tiene su propio \texttt{Condition} para esperar que su equipo se complete sin bloquear a otros visitantes.
    \item La ticketera usa un \texttt{Semaphore} y un \texttt{Exchanger} para manejar la actualización de la billetera del visitante de manera segura.
\end{itemize}

\section{Estrategias de Prevención de Problemas de Concurrencia}

\subsection{Deadlock}

El deadlock ocurre cuando dos o más hilos quedan esperando indefinidamente por recursos que el otro tiene. Para evitarlo, el sistema implementa las siguientes estrategias:

\begin{itemize}
    \item \textbf{Orden estricto de adquisición de locks}: En el Comedor, nunca se adquiere el lock del Comedor desde dentro del lock de una Mesa. La notificación al Comedor se hace fuera del bloqueo de la mesa.
    \item \textbf{Timeouts en bloqueos}: Los Semaphore con \texttt{tryAcquire()} permiten abandonar colas de espera saturadas (ej: Montaña Rusa con cola llena).
    \item \textbf{Un solo punto de sincronización por operación}: Cada atracción maneja su propia lógica de sincronización de forma independiente.
\end{itemize}

\subsection{Inanición (Starvation)}

La inanición ocurre cuando un hilo nunca obtiene acceso a un recurso compartido. El sistema la previene mediante:

\begin{itemize}
    \item \textbf{Fairness en Semáforos}: Todos los \texttt{Semaphore} se crean con \texttt{fair = true}, garantizando que los hilos esperen en orden FIFO.
    \item \textbf{Exhaustividad de recursos}: Las colas de espera tienen límites; cuando están llenas, el visitante puede ir a otra atracción en lugar de esperar indefinidamente.
    \item \textbf{CyclicBarrier}: Garantiza que todos los participantes de un grupo avancen juntos.
\end{itemize}

\subsection{Livelock}

El livelock ocurre cuando los hilos están constantemente cambiando de estado pero no progresan. Se evita mediante:

\begin{itemize}
    \item \textbf{Condiciones de espera específicas}: Cada visitante espera en su propia \texttt{Condition}, no en un estado compartido activo.
    \item \textbf{No retoma automática de operaciones fallidas}: Si una operación no puede completarse, el hilo sale y puede reintentar más tarde.
\end{itemize}

\section{Conclusiones}

El sistema de parque de diversiones implementado demuestra el uso efectivo de múltiples mecanismos de sincronización de Java para resolver problemas de concurrencia reales. Cada atracción presenta desafíos únicos que requieren soluciones específicas:

\begin{itemize}
    \item \textbf{Montaña Rusa}: Manejo de colas con capacidad limitada y sincronización de grupos.
    \item \textbf{Autitos Chocadores}: Coordinación exacta de 20 personas para iniciar la atracción.
    \item \textbf{Realidad Virtual}: Gestión de recursos limitados (componentes) con espera individual.
    \item \textbf{Carrera de Gomones}: Flujo multi-etapa con coordinación de múltiples recursos.
    \item \textbf{Comedor}: Sincronización de inicio colectivo (todos comen juntos).
    \item \textbf{Teatro}: Formación de grupos y coordinación de espectáculo.
\end{itemize}

La combinación de Semaphores, Locks, Conditions, CyclicBarriers y Exchangers permite un sistema robusto que evita deadlocks, inanición y livelocks, garantizando que todos los visitantes puedan disfrutar de las atracciones de manera segura y justa.
